PLANO -- btp::Node como objeto unico do consumidor + cache de manifest
=====================================================================
Criado: 2026-09-25
Repos: BTP (lib), TraceView, bally_OS (so a etapa E5)
Base: BTP 2.47.0 (branch feature/node-multi-link)

VISAO GERAL
-----------
Hoje o btp::Node esta completo do lado PRODUTOR (robo: serve_catalog,
publish, SubscriptionTable, comandos, STATUS). Do lado CONSUMIDOR ele
cobre so HELLO e COMMAND. O TraceView contorna o Node e monta frame na
mao (header + ChannelSeal + BtpSession::sendFrame) em 6 lugares:

  componente TraceView       o que faz por fora do Node
  -------------------------  ------------------------------------------
  ManifestClient             MANIFEST_REQUEST/DATA, varios sources
  SubscriptionManager        SUBSCRIBE/UNSUBSCRIBE/renovacao/STATUS
  ClockSync                  COMMAND_REQUEST (set_clock)
  HubBinder                  COMMAND_REQUEST (bind de filho no dongle)
  BtpBackend::keepalive      MANIFEST_REQUEST "sentinela" so p/ gerar trafego
  BtpBackend::sessionClose   SESSION_CLOSE na mao
  BtpBackend::terminal       TERMINAL_IN na mao

E o receive e duplo: BtpSession -> ProtocolRouter (caminho principal)
e, em paralelo, uma copia "sombra" p/ m_node->receive().

Objetivo: o Node vira o unico ponto de entrada/saida BTP do consumidor.
Quem usa a lib (TraceView, dongle, terceiros) nao monta header, nao sela,
nao correlaciona request/result na mao. Junto, entra o cache de manifest
plugavel (hook no NodeConfig, desligado por padrao).

Fica FORA do Node (fronteira do library.md 16.11, mantida):
  - framing (COBS/serial/BLE) -> BtpSession continua so framing;
  - politica de roteamento de hub (repassar frame p/ filho);
  - agregacao N widgets -> 1 SUBSCRIBE (o Node ganha as primitivas,
    o refcount continua no app);
  - derivacao de chave (corpo do seal/open);
  - ONDE o cache e gravado (so o hook e da lib).

Versionamento: tudo aqui e MINOR (fio inalterado). E1+E2 = 2.48.0,
E3 = 2.49.0.


ETAPA E1 -- Consumidor de manifest multi-source (BTP 2.48.0)
------------------------------------------------------------
OBJETIVO
  O Node entrega cada MANIFEST_DATA de qualquer source ao app, em vez
  de so alimentar um Catalog unico (learn_catalog, que faz clear() a
  cada resposta e por isso nao serve para hub).

PASSOS
  1. Callback novo (padrao on_sample/on_terminal):
       using NodeManifestFn = void (*)(void* ctx, const NodeManifest& m);
       void Node::on_manifest(NodeManifestFn fn, void* ctx) noexcept;
     NodeManifest carrega:
       - header      : ManifestHeader da resposta que CHEGOU (boot_id,
                       source_info, uuid, revision sempre frescos);
       - payload     : ByteView do payload que chegou;
       - topics      : ByteView de onde ler os topicos (= payload numa
                       resposta completa; = blob do cache num NOT_MODIFIED);
       - from_cache  : bool;
       - link        : LinkRef de onde veio.
     So para status SUCCESS. Falha (NOT_FOUND/STALE_TARGET_BOOT/...)
     vai num evento separado: NodeRx::ManifestRejected + manifest_outcome()
     com (source_id, status, error_code), p/ o app limpar cooldown.
  2. receive() com on_manifest setado: consome o MANIFEST_DATA
     (NodeRx::ManifestHandled) em vez de devolver NodeRx::Complete.
     learn_catalog continua funcionando igual e pode coexistir.
  3. Nao interceptar o que o Node nao pediu? NAO: MANIFEST_DATA nao
     solicitado (announce_catalog, request reference zero) tambem e
     entregue -- e valido pela spec.

CRITERIOS DE ACEITE
  - Enumeracao target=0 de um hub com N robos -> N chamadas de
    on_manifest, nenhuma apaga a outra.
  - Codigo de produtor existente (bally_OS) compila sem mudanca.


ETAPA E2 -- Cache de manifest plugavel (BTP 2.48.0)
---------------------------------------------------
OBJETIVO
  O app decide ONDE guardar (arquivo, NVS, SD, nada); a lib decide
  QUANDO ler/gravar e como usar NOT_MODIFIED. Sem override = desligado,
  comportamento identico ao de hoje.

PASSOS
  1. Hooks no NodeConfig (mesmo padrao has_seal()/seal()):
       virtual bool has_manifest_cache() const noexcept { return false; }
       virtual bool manifest_load(uint32_t source_id,
                                  uint32_t* revision, uint8_t uuid[16],
                                  uint8_t* buf, size_t cap,
                                  size_t* len) noexcept;
       virtual void manifest_store(uint32_t source_id, uint32_t revision,
                                   const uint8_t uuid[16],
                                   const uint8_t* payload,
                                   size_t len) noexcept;
       virtual void manifest_evict(uint32_t source_id) noexcept;
     O valor guardado e o PAYLOAD CRU do MANIFEST_DATA completo (o
     formato de fio ja e a serializacao; nada de formato novo).
  2. request_manifest_cached(target_source_id, target_boot_id):
     chama manifest_load e preenche known_config_revision (0 se miss).
     request_manifest() atual fica intacto.
     target 0 (enumeracao) nao usa cache -- known_config_revision e por
     alvo na spec; o app deve preferir requests direcionados quando ja
     sabe quem existe (ex.: lista de peers do hub).
  3. Recebimento, com cache ligado:
     - completo SUCCESS -> manifest_store -> on_manifest(from_cache=0);
     - NOT_MODIFIED     -> manifest_load  -> on_manifest(from_cache=1,
                           header = resposta nova, topics = cache);
     - NOT_MODIFIED e load falhou (cache apagado no meio) ->
                           manifest_evict + re-request revision 0;
     - uuid da resposta != uuid do cache -> manifest_evict + re-request
                           revision 0 (outro aparelho, mesmo source_id).
  4. learn_catalog + cache: Catalog::ingest() num NOT_MODIFIED hoje
     "mantem o que tem" -- mas apos reiniciar o consumidor o Catalog
     esta vazio. Com cache, o Node faz ingest do blob do cache nesse
     caso. (Bug latente que o cache expoe; corrigir aqui.)
  5. Buffer: manifest_load escreve no scratch_buffer_ do Node (ja
     dimensionado p/ MANIFEST_DATA no StaticNode). Sem scratch ->
     cache tratado como desligado.
  6. Node::connected_peer_uuid(uint8_t out[16]) -- ja decodificado no
     HELLO_RESULT, so nao exposto.

CRITERIOS DE ACEITE
  - Consumidor com cache em memoria: 2a sessao com mesma revision
    recebe NOT_MODIFIED e on_manifest(from_cache=1) com topicos certos
    e boot_id novo.
  - Revision diferente -> resposta completa, cache regravado.
  - uuid trocado -> evict + re-request automatico.


ETAPA E3 -- Resto do consumidor dentro do Node (BTP 2.49.0)
-----------------------------------------------------------
OBJETIVO
  Fechar os outros contornos do TraceView, para o Node ser o unico
  objeto. Cada item e independente; ordem sugerida abaixo.

PASSOS
  1. Keepalive de verdade. Hoje o TraceView manda um MANIFEST_REQUEST
     p/ um source inexistente (ou boot_id errado, no TCP/BLE direto)
     so para gerar resposta e alimentar o watchdog. O Node ganha
     enable_keepalive(period_ms): no tick(), sem trafego enviado ha
     period_ms e com sessao ativa, manda o "ping" que a spec permite.
     >> DECISAO: a spec nao tem PING dedicado. Opcoes:
        (a) formalizar o truque atual dentro do Node (MANIFEST_REQUEST
            p/ o proprio peer com boot_id errado -> STALE_TARGET_BOOT);
        (b) adicionar um PING/PONG CONTROL na spec (MINOR, object_id novo,
            exige firmware atualizado nos dois lados).
        Recomendo (a) agora, (b) quando houver outra mudanca de spec.
  2. SESSION_CLOSE: BtpBackend::requestSessionClose -> Node::disconnect()
     (ja existe). So migracao no TraceView, nada na lib.
  3. TERMINAL_IN: Node::send_terminal(bytes) com chunking p/ o limite
     negociado (hoje o TraceView corta em 1 KB na mao). Selagem via
     cfg.seal como todo o resto.
  4. Comandos: CommandClient do Node ja suporta varios slots. Verificar
     se o TraceView habilita >= 3 slots (comando do usuario + ClockSync
     + HubBinder simultaneos) e migrar ClockSync/HubBinder p/
     node.command() + command_outcome(). Nada na lib, provavelmente.
  5. Assinaturas: SubscriptionClient ganha
       bool resubscribe(uint32_t local_id, uint32_t rate_millihz, ...);
     (SUBSCRIBE com a mesma sessao+topico substitui atomicamente,
     commands.md 4). E a unica coisa que faltava p/ o SubscriptionManager
     do TraceView usar o Node -- o refcount de widgets continua no app.
     Mais: entrega de STATUS recebido ao app (on_status(fn, ctx)).
  6. Receive unico: com 1-5 prontos, o Node vira o caminho PRINCIPAL.
     BtpSession fica so framing; ProtocolRouter passa a ser alimentado
     pelo que o Node devolve como NodeRx::Complete (telemetria, log).
     O repasse de frame cru p/ filhos de hub continua como esta.

CRITERIOS DE ACEITE
  - TraceView sem nenhum btp::Header montado a mao fora de testes.
  - ChannelSeal usado so dentro de BtpBackend::seal()/open().
